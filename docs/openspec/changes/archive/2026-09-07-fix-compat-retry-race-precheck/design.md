# 设计：修复禁流重试竞态误判与前置检查"正在充电"行误导

## Context

根因见 proposal.md。关键事实：①daemon 重试写应答（约 1 秒）与写生效（IsCharging 翻转，再需 2~3 秒）之间存在**生效滞后窗口**，上一轮的恢复判定把滞后采样当成新恢复事件；②确认窗口重开时机错误：写完成即重开，滞后样本直接落入新窗口；③daemon 自身重试上限 `kDisableInflowRetryMaxAttempts = 3`（0.6 秒间隔，可重新武装），引擎保持 3 次上限即可；④前置检查"正在充电"行与引擎"自动恢复充电基线"能力重复，回稳慢时第二次点开始显示橙色"未在充电"造成误读。

## 修复方案（单一方案）

1. **确认窗口自「写生效」起算**：禁流测试进入确认阶段时窗口关闭（`confirmStartIndex = -1`），首个非充电样本（`!(isCharging && current ≥5mA)`）开窗并以该样本初始化判定窗口统计。停充/智能停充保持"状态变化样本即窗口起点"的原逻辑不动。
2. **恢复事件门控**：充电恢复（`isCharging && current ≥ CLCompatCurrentThresholdmA`）仅在窗口已建立（生效已被观察到）时计为恢复事件 → 走重下发/耗尽分支。窗口未建立（写生效滞后观察期）时，滞后样本不计恢复、不计入判定窗口统计，仅累计连续充电采样数 `inflowChargeStreak`。
3. **生效观察上限**：`inflowChargeStreak ≥ CLCompatConfirmWindow`（10 个连续充电采样；重试写在途时暂停计数）→ 等效恢复事件处理（重下发或耗尽判定）。保证"写无效/生效极慢"路径可终止。
4. **重试写完成仅清 `inflowRetryInFlight`**：不再重置窗口与统计（窗口由生效样本重开）；`beginWrite/endWrite` 在途计数保留（abort 排水依赖）。
5. **前置检查**：移除"正在充电"行（`precheckRows[@"charging"]`）、`runPrecheckWithCompletion` 的 charging 项、失败文案映射与橙色特判；说明区删除前置检查时刻 tip；"请在插电且正在充电时运行"改"请在插电状态下运行"。

## Risks / Trade-offs

- [窗口起点从变化样本移到首个生效样本，支持判定最多晚 1 秒] → 换取窗口内不混入滞后样本，allBelow 可按 10 秒干净判定，结果卡不再显示滞后充电电流。
- [10 秒生效观察上限对生效极慢的设备偏紧] → 与确认窗口长度一致，只影响"是否计为恢复事件"而非直接判负；真机复测验证。
- [删除前置检查"正在充电"行后用户看不到充电状态] → 引擎自动恢复基线并在事件流提示"正在恢复充电基线…"，状态可见性由实时电流与事件流承担。
