# 提案：修复禁流重试竞态误判与前置检查"正在充电"行误导

## Why

Hotfix `fix-compat-inflow-retry` 后真机复测（用户实测，仅勾选禁流单项）：

1. **禁流测试实际成功但结论判不支持**：用户明确"禁流测试是成功的"——禁流测试的语义即"充电线不动、软件模拟拔线"，每次禁流写都生效、充电可见地停止；但结论输出失败。根因是**重试竞态**：重试写发出后 daemon 约 1 秒内应答（`inflowRetryInFlight` 清零、确认窗口重开），但 `IsCharging` 真正翻转还需 2~3 秒生效滞后；滞后窗口内的采样仍显示"正在充电、电流 ≥5mA"，被确认窗口段的恢复判定当成**新的**充电恢复事件 → 第 1 次真实恢复触发的重试 #1 刚写完，下一个滞后采样即被计为恢复 #2 → 重试 #2 → 又计为恢复 #3 → 重试 #3 → 再计 → 3 次耗尽 → 判"禁流无法维持：充电被系统恢复且重试已耗尽"。**一次真实恢复烧光全部 3 次重试**，成功测试被误判。
2. **前置检查"正在充电"行误导**：用户质疑"只测禁流这一项时，为什么前置检查要'正在充电'？禁流一生效它就变成出错"。该行显示的是点击开始时刻的快照；测试结束回稳慢时第二次点开始会如实显示"未在充电"（橙色），用户无法区分这是预期状态切换还是错误。而引擎开始时本就会自动恢复充电基线，该行从设计上冗余，只会造成误读。用户明确指示：开始测试之后充电状态的变化不要管。

**复现与自动化说明**：依赖真实设备充电状态机与写生效滞后时序，本环境无法自动化复现；证据为用户真机实测描述 + 代码级根因定位（`handleSample` 确认窗口段恢复判定，CLBatteryCompatibilityTestViewController.m:694-725）。

## What Changes

- **恢复事件仅计"生效后被恢复"**：确认窗口改为从「禁流生效被观察到」的采样起算（首个非充电样本开窗）。充电恢复判定（正在充电且电流 ≥5mA）仅在窗口已建立（即已观察到生效）时计为恢复事件；重试写完成不重置窗口，由下一个生效样本重开——写生效滞后期内的充电采样不计为新恢复。
- **写未生效的观察上限**：状态变化或重试下发后连续 10 秒（确认窗口长度）未观察到禁流生效（充电未被止住）→ 等效为充电被恢复处理（重下发或耗尽判定），保证路径可终止。
- **重试上限保持 3 次**（与 daemon 自身 `kDisableInflowRetryMaxAttempts` 一致）。
- **前置检查移除"正在充电"行**：删除该行、`runPrecheckWithCompletion` 的 charging 项、失败文案与充电态橙色特判；说明区删除"前置检查显示的是点击开始时的状态"提示；"请在插电且正在充电时运行"改为"请在插电状态下运行"。"正在充电"文案 key 被其他页面共用，保留 strings 条目。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `battery-compatibility-test`: 禁流测试判定（恢复事件以"生效后被恢复"计数、确认窗口自生效样本起算、写未生效观察上限）。需 delta spec。

## Impact

- 修改：`ChargeLimiter/UIKit/Controllers/CLBatteryCompatibilityTestViewController.m`（禁流确认窗口状态机、前置检查、说明区）、`en.lproj`、`zh-Hans.lproj`（删 2 个失效 key、改 1 个 tip key）。
- 复用不改：daemon 全部 API；停充/智能停充确认窗口逻辑保持不动。
