# Brainstorm Summary

- Change: fix-lockscreen-limit-inflow
- Date: 2026-08-19

## 已确认事实

- 原版仅在充电命令边沿写入 thermal mode，不根据锁屏、电池读数或适配器读数持续推导状态。
- `1.7` 至 `v1.12.4` 的产品语义对应方案 1：`setBatteryStatus(YES)` 使用限流档，`setBatteryStatus(NO)` 使用默认档；限流开关或等级变化不会立即应用，默认档变化会无条件立即写入。
- `d8ad775` 引入 `desired -> sync` 闭环后，电池事件开始反复重写 thermal pref；后续锁屏修复都在这个错误闭环内增加判断和状态。
- `d8ad775` 位于 `v1.12.4` 与 `v1.12.5` 之间，因此 `v1.13.x`、`v1.14.x` 均包含该闭环。`v1.14.2` 仍以方案 1 为目标，但用“适配器已连接且（充电命令允许或 IsCharging）”推导是否应用限流档。
- `v1.14.2` 会在四个 thermal 配置键变化时立即重算，改善了切换体验，但 UI 的限流选择会连续发送开关和等级两个请求，期间可能先写旧档再写新档。
- `v1.15.1` 去掉适配器前置并加入电流判断；`v1.15.2` 又恢复适配器前置、加入去抖、读回与周期自愈。各版本目标仍接近方案 1，但越来越依赖不可靠运行时读数。
- `b8c0764` 删除了闭环、自愈、读回、粘滞状态与传感器阈值，恢复了原版命令驱动语义。
- 当前回退稿仍有切换缺口：修改 `adv_def_thermal_mode` 会无条件覆盖当前限流档；修改限流开关、限流等级或锁定开关不会立即应用。
- UI 选择限流等级时会连续发送 `adv_limit_inflow` 与 `adv_limit_inflow_mode` 两个 `set_conf` 请求。

## 候选技术方向（待确认）

- 保留命令边沿作为 thermal mode 的唯一运行态依据。
- 配置变化时只依据配置和 `g_chargeCommandEnabled` 重新应用一次目标档位，不读取锁屏、适配器、电流、`IsCharging` 或其他电池信号。
- 对 UI 的双配置请求做短去抖，只应用最终配置，避免先写旧等级再写新等级。
- 不恢复 desired 闭环、周期自愈、pref 读回、粘滞状态或锁屏专用逻辑。

## 关键取舍与风险

- 优先保证行为可预测：命令说“充电”时使用限流档，命令说“停充”时使用默认档。
- UI 一次选择会分别写 `adv_limit_inflow`（布尔开关）和 `adv_limit_inflow_mode`（档位字符串）。客户端把它们作为两个独立 `NSURLSessionDataTask` 发出，daemon 只串行处理单个请求，不提供跨请求事务。
- 配置去抖是短暂的最终态合并，不承担运行态维护：最后一个请求处理后等待约 200ms，再读取两个配置的最终组合并应用一次。代价是约 200ms 延迟，且请求间隔超过窗口或其中一个失败时仍不具备原子性。
- 更严格的备选是增加一次性保存“限流开关 + 档位”的批量接口；它真正原子且无需去抖，但会扩大到 UI、API 和 daemon 多文件修改。
- 真机锁屏保持仍需验收，但实现不再识别或处理锁屏状态。

## 测试策略（候选）

- 源码契约测试：配置应用不得读取电池、适配器或锁屏相关信号。
- 行为矩阵：充电/停充命令状态与限流开关、等级、锁定开关组合得到确定档位。
- 回归测试：连续更新限流开关与等级只应用最终配置。
- 三个 scheme 编译；真机覆盖充电中切换、停充时切换、锁屏保持。
